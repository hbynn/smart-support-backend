# EchoMind 售后工单改造学习指南

这次改造将 EchoMind 从“只生成客服回答”扩展为“可以安全执行退款任务”的系统。

## 1. 核心设计

```text
创建工单
  -> 提取订单号和退款金额
  -> 查询订单
  -> 校验退款资格
  -> 生成带幂等键的执行计划
  -> 高风险退款等待人工审批
  -> 执行退款
  -> 按幂等键确认结果
  -> 完成工单并保留审计记录
```

退款金额达到 `REFUND_APPROVAL_THRESHOLD`（默认100元）时，必须人工审批；低金额退款可以自动执行。

## 2. 每个代码文件的作用

### `domain/models.py`

定义业务数据，不包含数据库和HTTP逻辑：

- `Order`：演示订单。
- `Ticket`：一次售后任务及其当前状态。
- `RefundRecord`：已经执行的退款结果。
- `AuditEvent`：谁在什么时候做了什么操作。
- `TicketState`：工单状态枚举。
- `RiskLevel`：决定是否需要人工审批。

领域模型独立后，可以在不启动FastAPI和LLM的情况下测试工作流。

### `domain/repository.py`

负责SQLite持久化和事务：

- 初始化 `orders`、`tickets`、`refunds`、`audit_events` 四张表。
- 写入三条演示订单。
- 使用 `request_key` 唯一约束阻止相同逻辑请求创建多张工单。
- 使用 `idempotency_key` 唯一约束阻止重复退款。
- 使用 `version` 做乐观锁，防止并发审批覆盖。
- 将同步 `sqlite3` 操作放入 `asyncio.to_thread()`。

`create_refund_once()` 在一个事务中写退款记录并修改订单状态。两步要么一起成功，要么一起回滚。

### `tooling/support_tools.py`

提供五个业务工具：

| 工具 | 类型 | 作用 |
|---|---|---|
| `get_order` | 读 | 查询并校验订单所属用户 |
| `get_logistics` | 读 | 查询演示物流状态 |
| `check_refund_eligibility` | 读 | 校验订单状态和退款金额 |
| `create_refund` | 写 | 执行经过规划和审批的退款 |
| `get_refund_status` | 读 | 按幂等键确认退款结果 |

这些工具注册进原有 `MCPToolManager`，因此自动获得参数校验、超时、熔断和运行指标。

`create_refund` 会再次检查工单状态、审批信息和规划参数。即使调用方绕过Workflow，也不能直接执行高风险退款。

### `workflow/ticket_workflow.py`

负责业务流程和状态转换：

```text
CREATED
  -> COLLECTING_INFO（缺订单号）
  -> PLANNING
  -> WAITING_APPROVAL（高风险）
  -> EXECUTING
  -> VERIFYING
  -> RESOLVED / FAILED
```

重要方法：

- `create_ticket()`：创建或返回重复工单。
- `supply_details()`：补充缺失订单信息。
- `approve()` / `reject()`：处理人工审批。
- `retry()`：先确认旧请求结果，再使用原幂等键重试。
- `_plan()`：查询订单、检查资格并生成执行计划。
- `_execute_refund()`：调用写工具，结果未知时进入确认阶段。
- `_verify_refund()`：通过幂等键确认最终状态。

### `audit/audit_logger.py`

把状态变化和敏感操作持久化为审计事件。应用日志用于排错，审计日志用于回答：

- 谁批准了退款？
- 是否出现绕过审批的调用？
- 同一个请求是否被重复提交？
- 工单在哪一步失败？

### `api/main.py`

在应用启动时初始化Repository、业务工具和Workflow，并暴露工单接口。HTTP层只负责请求校验、调用Workflow和异常映射，不直接写数据库。

### `tests/test_ticket_workflow.py`

覆盖四条关键路径：

- 高风险退款必须审批，且不能绕过Workflow。
- 低风险退款自动执行。
- 缺订单号时先补充资料。
- 被拒绝的工单不能再次审批。

测试使用临时SQLite数据库，不调用外部LLM。

## 4. API演示

### 创建高风险退款工单

```bash
curl -X POST http://localhost:8000/tickets \
  -H "Content-Type: application/json" \
  -d '{"user_id":"user_001","message":"订单A12345退款200元"}'
```

预期状态：

```text
WAITING_APPROVAL
```

### 人工审批

```bash
curl -X POST http://localhost:8000/tickets/<ticket_id>/approve \
  -H "Content-Type: application/json" \
  -d '{"actor":"manager_001"}'
```

预期状态：

```text
RESOLVED
```

### 查看审计记录

```bash
curl http://localhost:8000/tickets/<ticket_id>/audit
```

### 重复提交

再次提交同一用户、订单和金额，接口会返回原来的 `ticket_id`，不会创建第二笔退款。

## 5. 面试表达

> 我将原有回答型客服改造成可执行售后工单系统。使用持久化状态机控制信息收集、任务规划、人工审批、工具执行和结果确认；通过任务级request_key避免重复建单，通过操作级idempotency_key和数据库唯一约束避免重复退款。高风险写操作在Workflow和Tool两层校验审批，退款接口超时时先按幂等键确认结果，而不是盲目重试。所有状态变化写入审计表，便于定位审批绕过和执行故障。

## 6. 当前边界

- SQLite和订单数据用于本地演示，生产环境应替换为订单服务与PostgreSQL。
- 当前退款执行是本地事务模拟，没有连接真实支付平台。
- 工单工作流目前由专用API触发，后续可以让Chat Agent生成结构化计划后调用Workflow。
- 当前使用项目内部ToolManager，尚不是完整标准MCP协议实现。
