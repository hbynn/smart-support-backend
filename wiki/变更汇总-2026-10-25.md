## 2. 在线意图向量检查与诊断

### 2.1 独立开关和检查入口

- 新增 `INTENT_EMBEDDING_ENABLED`，默认 `true`。
- 设为 `false` 时跳过整个向量分支，使用 LLM 0.85、规则 0.15 的融合权重，实际来源标记为 `disabled`。
- `INTENT_EMBEDDING_PROVIDER=local` 只切换到本地向量，不关闭向量分支，仍使用三路融合。
- 新增 `POST /integrations/embedding/check`，独立检查模板和问题向量，不调用聊天模型，也不写入意图识别结果缓存。
- 新增 `scripts/check_embedding.py`，从项目根目录加载 `.env`，支持从其他工作目录运行。只有实际使用在线 BAAI 模型时退出码为 0；关闭或本地降级时为 1。
- API 启动入口也改为显式加载项目根目录 `.env`，避免工作目录变化导致配置未读取。

### 2.2 真实来源与降级原因

向量状态补充以下字段：

| 字段 | 含义 |
|---|---|
| `branch_enabled` | 是否执行向量分支，由状态接口补充 |
| `last_source` | 最近一次实际使用的向量来源 |
| `last_dimensions` | 最近一次向量维度 |
| `fallback_reason` | 缺少 Key、主动本地模式、HTTP 错误或超时等降级原因 |
| `retry_after_s` | 距离允许重新尝试在线请求的时间 |

聊天意图结果进一步区分 `siliconflow/BAAI/bge-m3`、`local-ngram`、`disabled` 和 `unavailable`。在线失败日志只记录错误类别或状态码，不记录可能带认证信息的完整异常正文。

本次主要补齐已有 BAAI 接入的诊断和验证能力。BAAI 仍只用于意图识别；知识库和长期记忆仍使用 ChromaDB 默认向量模型，没有迁移既有索引。

## 3. DeepSeek 短输出兼容修复

### 问题

实际请求确认：DeepSeek 默认思考模式会与最终正文共用输出预算。部分 256 token 的分类请求达到 `max_tokens` 时只返回思考内容，没有可解析的 JSON，随后触发意图回退；画像、查询改写等短输出任务也可能出现类似问题。

### 修改

- 在 `core/llm_utils.py` 新增统一的 `create_message()` 调用入口。
- 对 `api.deepseek.com` 默认通过 `extra_body` 显式发送 `thinking.type=disabled`，兼容项目固定版本的 Anthropic SDK。
- 保留调用方显式指定的思考配置；其他服务商的请求参数不自动改变。
- 意图识别、各 Agent、Composer、查询改写、重排、画像、摘要和 Judge 均改用统一入口。
- 真实回复达到 token 上限时，原有 `partial` 状态处理仍然保留，没有通过返回后截断或修改状态掩盖问题。

## 4. 响应速度与模型调用量优化

### 4.1 缓存完整检索流程

原有缓存只覆盖底层工具调用；同一个查询再次执行时，仍会调用模型改写查询，并可能再次重排。

本次在 `search_with_rewrite()` 增加完整流程缓存，覆盖“查询改写 → 并行召回 → 去重 → 重排”：

- 缓存按查询、Top-K、工具版本和传入的用户上下文隔离。
- 同进程内的相同并发检索通过按键锁合并，等待者命中已计算结果。
- 返回缓存数据的深拷贝，防止调用方修改共享结果。
- 知识库更新沿用原有失效入口；版本检查防止失效前的在途请求重新写回旧结果。
- 失败检索不缓存；工具 TTL 为 0 时同时关闭完整流程缓存和并发合并。
- 线上与评测管理器的缓存及按键锁保持独立。
- `/search` 和共享知识库工具结果增加 `cached`，表示是否命中完整流程缓存。

首次检索仍执行原有改写和重排流程，没有通过跳过召回步骤换取速度。

### 4.2 后台画像限频

- 新增 `PROFILE_UPDATE_MIN_INTERVAL_S`，默认 60 秒。
- 普通后台画像在间隔内不重复提炼；识别到“请记住”“以后请”“我喜欢”等明确偏好表达时允许立即更新。
- 显式调用 `update_profile()` 默认仍可强制更新；设间隔为 0 可恢复逐轮更新。
- 时间标记保存在 Redis，并在用户画像锁内检查；只有成功更新后才写入，失败不会抑制后续重试。
- 会话消息、业务字段仍逐轮保存，记忆压缩仍按原有条件运行。

### 4.3 减少重复输入与冗长输出

- 优先通过角色输入包传递结构化实体，避免再发送一份重复实体消息及确认语。
- 默认回复提示约 200–400 个中文字符，多角色汇总约 300–500 个字符。
- 保留必要依据、核验条件、处理边界和下一步；用户要求详细时允许展开。
- 提示模型避免重复背景、大表格及内部检索分数等无关信息。

篇幅是生成提示，不是硬裁剪，不保证每条回复严格满足字符范围。

## 5. 性能与 token 观测

新增 `core/performance.py`，通过 `ContextVar` 隔离请求统计，并允许同一请求的并行任务共同记录：

- 聊天响应新增 `performance`。
- `stages_ms` 记录记忆读取、意图识别、Agent 执行及实际触发的检索阶段耗时。
- `llm_calls` 记录阶段、模型、状态、调用耗时和供应商报告的 token 数，不保存提示词或异常正文。
- `llm` 汇总逻辑调用次数、错误数、token 和已报告用量的调用数。
- `/monitor` 新增 `llm_usage.by_stage`，按阶段累计本进程用量，包括后台画像。
- 每个模型调用入口标注 `intent`、`agent.*`、`composer`、`rag.*`、`memory.*` 或 `evaluation.judge` 阶段。

统计口径：

1. 阶段存在嵌套，不能直接相加；并行模型调用的耗时之和也不等于实际响应时间。
2. 响应中的阶段统计截止生成回复，完整 HTTP 耗时（含提交）仍查看 `Server-Timing`。
3. 幂等回放保留原响应统计，不代表重新发生了相同模型请求。
4. 调用次数按 SDK 逻辑调用计数，不展开 SDK 内部重试。
5. token 字段采用供应商口径，缓存 token 单独记录；未报告的用量不估算，不直接换算账单金额。
6. 进程统计重启后重新累计；完整检索缓存及并发合并也为进程内机制。

### 性能对照

| 场景 | 优化前 | 优化后 |
|---|---:|---:|
| 相同知识查询连续 3 次：模型调用 | 6 次 | 2 次 |
| 相同知识查询连续 3 次：累计耗时 | 10,082.5 ms | 2,829.8 ms |
